# M6 造数、压测、双实例演示

## 这个里程碑做了什么

前五个里程碑做的是"功能对不对"，这个里程碑回答"设计好不好"。先用一个 `datagen` profile 的 CommandLineRunner 按 SPEC 规模造数（1 万用户、5 万文章、30 万关注其中 4 个大 V 各 6000 粉丝、30 万点赞、6 万收藏、10 万评论），JDBC 批量插入加 `rewriteBatchedStatements=true`，固定随机种子保证每次数据一样，在本机约 45 秒完成。然后用 JMeter（跑在 Docker 里，不用安装）对 SPEC 14.2 的 5 个场景做对比压测：缓存模式、计数策略、Feed 读、大 V 扇出、限流，每组 3 次取中位数，结果写进 `docs/perf-report.md`。最后用 `--scale backend=2` 起两个后端实例，验证两级缓存失效广播、SSE 跨实例推送和定时任务单实例执行。

## 知识点清单

### 1. 批量插入为什么要 `rewriteBatchedStatements=true`
- **是什么**：MySQL JDBC 驱动默认把 `addBatch` 的多条 INSERT 逐条发给服务器，只是省了 Java 侧的调用开销；打开这个参数后，驱动把它们改写成一条 `INSERT … VALUES (…), (…), …`，网络往返和服务器解析次数都降到几百分之一。
- **在哪**：`backend/code-nest-web/src/main/resources/application.yml:18`（连接串）、`web/datagen/DataGenerator.java:417`（每 2000 行一批）。
- **怎么验证**：把连接串里的这个参数去掉，删掉数据卷重新造数，对比日志里的耗时。

### 2. 造数要"像真的"
- **是什么**：均匀随机的数据压不出热点。造数时文章的点赞按"热度偏斜"分布（少数文章拿走大部分点赞），关注关系里有 4 个大 V，文章发布时间分布在近 180 天。计数表不是边插边累加，而是插完后用聚合 SQL 一次重建，最后预热排行榜和热门文章。
- **在哪**：`web/datagen/DataGenerator.java:89`（主流程）、`:204`（关注与大 V）、`:432`（热度偏斜）、`:348`（重建计数）、`:379`（预热）。
- **怎么验证**：`SELECT followee_id, COUNT(*) c FROM follow GROUP BY followee_id ORDER BY c DESC LIMIT 5;`。

### 3. 压测方法：控制变量
- **是什么**：每个场景只改一个变量（例如缓存模式），其他条件不变；改完先预热，再跑 3 次取中位数（避免偶发的 GC 或磁盘抖动）；记录机器配置和线程数；结论只看相对变化，不看绝对值。
- **在哪**：`perf/run.sh`（每个场景一个函数）、`perf/tools/summarize.py`（分位数与中位数）、`perf/tools/gen_plans.py`（生成 JMeter 计划）。
- **怎么验证**：`RUNS=1 THREADS=20 DURATION=10 bash perf/run.sh 1` 快速跑一遍场景 1。

### 4. 吞吐、平均值和分位数
- **是什么**：平均值会被少数慢请求拉高，也会掩盖长尾；P95 / P99 表示 95% / 99% 的请求不超过这个耗时，更能反映用户体验。吞吐要和错误率一起看：错误请求往往返回得很快，会让吞吐"虚高"。
- **在哪**：`perf/tools/summarize.py:14`。
- **怎么验证**：对比 `docs/perf-report.md` 里场景 1 三种模式的 P50 和 P99 的差距。

### 5. 压测发现的问题：连接池
- **是什么**：第一轮压测时缓存场景有 7%～12% 的 500 错误，原因是 Lettuce 在没有连接池时，每次 pipeline 都新建一条连接。功能测试和单元测试都发现不了这个问题。
- **在哪**：pitfalls P-017；`application.yml` 里的 `spring.data.redis.lettuce.pool`。
- **怎么验证**：把 `pool.enabled` 改成 false 重跑场景 1，错误率会回来。

### 6. 两级缓存的失效广播（双实例）
- **是什么**：每个实例有自己的 Caffeine 本地缓存。一个实例修改文章后删除自己的本地缓存和 Redis，并在 Redis 频道里广播这个 key；另一个实例收到后删除自己的本地副本。
- **在哪**：`service/cache/CacheService.java:97`、`:244`。
- **怎么验证**：见下方"双实例演示"第 2 步。

### 7. SSE 跨实例推送（双实例）
- **是什么**：SSE 长连接只存在于某一个实例。产生通知的消费者把"用户:未读数"发到 Redis 频道，所有实例都收到，只有持有该用户连接的实例推送。
- **在哪**：`service/notify/NotifyService.java:172`、`web/sse/SseHub.java:40`。
- **怎么验证**：见下方第 3 步。

### 8. 定时任务只在一个实例执行（双实例）
- **是什么**：`@Scheduled` 在每个实例上都会触发。用 Redisson 的 `tryLock()`（不等待，拿不到就跳过）保证同一时刻只有一个实例执行；Redisson 的看门狗会给持有的锁自动续期，任务执行时间长也不会中途失效。
- **只有锁还不够**：锁只保证"不同时跑"。两个实例的定时器相差几百毫秒触发，任务又几十毫秒就跑完，后到的实例在锁释放后照样能再跑一遍。所以低频任务拿到锁后还要 `SET NX` 一个带过期时间的"本周期已执行"标记（类似 ShedLock 的 lockAtLeastFor），这是做双实例演示时发现并修复的（P-018）。
- **在哪**：`core/lock/JobLock.java`（`runExclusively` 的两个重载）、`web/job/ScheduledJobs.java:53`。
- **怎么验证**：跑 `IT/JobLockIT.java`，第一个测试证明"只有锁会跑两次"，第二个证明加了最短间隔只跑一次；再看下方第 4 步。

## 双实例演示步骤

```bash
docker compose up -d --build --scale backend=2
docker compose restart frontend          # Nginx 启动时解析 backend，重启后才能拿到两个地址
docker compose ps backend                # 两个实例：code-nest-backend-1、code-nest-backend-2
```

1. **请求被分到两个实例**：两个实例在宿主机上分别映射到 8081 和 8082。经 Nginx 请求几十次 `http://localhost:8080/api/categories`，再分别打开 `http://localhost:8081/actuator/metrics/http.server.requests?tag=uri:/api/categories` 和 8082 的同一地址，两个 COUNT 加起来等于总次数，而且大致各一半。
2. **缓存失效广播**：分别打开 `http://localhost:8081/api/articles/<id>` 和 `http://localhost:8082/api/articles/<id>`，让两个实例的本地缓存都存上这篇文章。然后登录作者，在前端修改标题，立刻再分别打开这两个地址：都是新标题。本地缓存 TTL 是 60 秒，没处理修改请求的那个实例能立刻读到新值，只能是因为它收到了 Redis 广播、清掉了自己的本地副本。可以把 `CacheService.subscribe()` 里的 `local.invalidate(key)` 注释掉再试一次作对比。
3. **SSE 跨实例**：用 `curl -N http://localhost:8082/api/notifications/stream -H "Authorization: Bearer <作者的令牌>"` 在 8082 上建立连接，再用另一个用户的令牌调用 `POST http://localhost:8081/api/articles/<id>/like`。8082 上的连接会收到 `event:unread`，数字加 1。
4. **定时任务单实例**：`docker compose logs backend | grep "hot articles refreshed"`，启动 30 秒后只有一个实例打印这一行；`redis-cli --scan --pattern "*job*"` 能看到 `lock:job:hot-score:ran` 标记。

实际验证结果记录在 `docs/perf-report.md` 最后一节。

## 面试可能怎么问

1. **你是怎么做压测的？结果可信吗？**
   原理：控制变量、预热、多次取中位数、记录环境、看分位数和错误率。本项目：JMeter 在 Docker 里跑，5 个场景每组 3 次。局限：压测机和被测服务在同一台机器上，会互相抢 CPU，绝对值没有参考意义，只看相对变化；数据量也远小于真实生产。

2. **缓存带来了多少提升？**
   原理：省掉了数据库查询和对象组装。本项目：场景 1 中 redis 模式吞吐约为 none 的 2.8 倍，two-level 再提升约 15%，P99 从 171ms 降到 44ms（具体以报告为准）。局限：90% 请求集中在 10 篇文章，命中率极高，真实流量的分布没有这么集中。

3. **为什么 redis-batch 的数据库写入只有个位数？**
   原理：1000 次阅读都只改 Redis，10 秒一次的写回把同一篇文章的多次修改合并成一次 upsert。本项目：场景 2 中 atomic-sql 写库 1000 次，redis-batch 只有几次。局限：写回间隔内 Redis 宕机且未持久化会丢数据。

4. **大 V 发文时推模式有什么问题？**
   原理：粉丝数 N 就要写 N 个收件箱，耗时和内存都随 N 线性增长。本项目：场景 4 测出 6000 粉丝的扇出耗时和内存增量，hybrid 模式不扇出。局限：本项目最大的大 V 只有 6000 粉丝，百万粉丝时差距会大得多。

5. **压测中遇到过什么问题？**
   本项目：Redis 连接在高并发下被打满（pipeline 每次新建连接），开连接池解决（P-017）；登录接口的限流挡住了压测准备脚本，新增 perf profile 放宽（P-015）。这类问题只有压测才能暴露。

6. **多实例部署要注意哪些问题？**
   原理：凡是"存在内存里"的东西都要考虑：本地缓存、长连接、定时任务、内存中的配置。本项目：本地缓存用 Pub/Sub 广播失效，SSE 用 Pub/Sub 路由，定时任务用分布式锁，运行时策略用 Pub/Sub 同步。局限：Pub/Sub 不保证送达，靠短 TTL 和客户端重连兜底。

7. **分布式锁的 `tryLock()` 和 `lock()` 有什么区别？定时任务为什么用 `tryLock()`？**
   原理：`lock()` 会阻塞等待，`tryLock()` 拿不到立即返回。本项目：另一个实例正在执行同一个任务时，这一轮直接跳过即可，等待没有意义。但 `tryLock()` 也只能挡住"同时"，挡不住"先后"：先到的实例跑完释放锁，后到的照样能跑，所以还需要一个带过期时间的"本周期已执行"标记（P-018）。局限：锁依赖 Redis，Redis 主从切换时可能短暂出现两个实例同时持锁——所以任务本身也要设计成幂等的（例如计数写回写的是绝对值）。
