# M1 账号与文章

## 这个里程碑做了什么

实现账号体系和文章的完整生命周期。账号用"短期访问令牌（JWT，30 分钟）+ 长期刷新令牌（存 Redis，7 天）"的双令牌方案：访问令牌无状态、校验快；刷新令牌每用一次就轮换，被盗最多只能用一次。登录连续失败 5 次锁 15 分钟；封禁通过"用户状态缓存 + 作废全部刷新令牌"做到立即生效。文章有草稿、待审、已发布、已下架等状态，发布接口用一次性提交令牌防止重复提交；头像和配图上传到 MinIO，按文件头魔数判断真实类型。前端完成登录、注册、首页、详情、编辑器（md-editor-v3，草稿自动保存）、设置页，并在拦截器里实现"令牌过期自动刷新再重试"。

## 知识点清单

### 1. JWT 访问令牌
- **是什么**：服务端用 HS256 密钥签名，载荷里放用户 ID 和角色。校验只需验签，不用查库，所以快；代价是签发后无法撤销，只能靠短有效期。
- **在哪**：`core/security/JwtUtil.java:44`（`createAccessToken`，签发）、`:57`（`parse`，解析，过期和其他无效分开处理）。
- **怎么验证**：登录后把 `accessToken` 粘到 https://jwt.io 看载荷；把 `application.yml:118`（`access-ttl`）的 `app.jwt.access-ttl` 改成 `1m`（或看 `IT/AuthIT.java:44`（`expiredAccessTokenIsRejectedWithRefreshableCode`）这个测试怎么"拨回时钟"造出过期令牌），再请求接口会得到 `code=20005`。

### 2. 刷新令牌轮换
- **是什么**：刷新令牌格式是 `userId.随机串`，Redis 里存 `refresh:{userId}:{随机串}`。刷新时用 `DEL` 的返回值判断"是否存在并删除"——这一步是原子的，两个并发刷新只有一个成功。成功后签发新的一对。
- **在哪**：`service/user/AuthService.java:84`（`refresh`）。
- **怎么验证**：跑 `IT/AuthIT.java:58`（`refreshTokenRotatesAndOldOneIsInvalid`）；或者手动用同一个 refreshToken 调两次 `/api/auth/refresh`，第二次返回 20006。

### 3. 登录失败锁定
- **是什么**：Redis `INCR login:fail:{username}`，第一次失败时设置 15 分钟过期；达到 5 次后连正确密码也拒绝。用户不存在和密码错误返回同一个提示，防止枚举用户名。
- **在哪**：`service/user/AuthService.java:64`（`login`）、`:131`（`recordFailure`）。
- **怎么验证**：跑 `IT/AuthIT.java:73`（`accountLockedAfterFiveFailures`）；或在 Redis 里 `GET code-nest:login:fail:xxx` 看计数和 `TTL`。

### 4. 封禁立即生效
- **是什么**：JWT 本身撤销不了，所以拦截器每个请求都查一次用户状态（Redis 缓存 `user:status:{id}`，未命中才查库）。封禁时改写这个缓存并作废全部刷新令牌（用 `SCAN` 而不是 `KEYS`，不阻塞 Redis）。
- **在哪**：`web/interceptor/AuthInterceptor.java:68`（`resolveUser`）、`service/admin/AdminService.java:69`（`ban`）、`service/user/AuthService.java:111`（`revokeAll`）、`service/user/UserStatusService.java:27`（`status`）。
- **怎么验证**：跑 `IT/AuthIT.java:87`（`adminEndpointsRequireAdminAndBanTakesEffect`）；或在管理端封禁一个已登录的用户，该用户下一次请求立即得到 `code=20004`。

### 5. 前端单飞刷新（single-flight）
- **是什么**：页面同时发 5 个请求都遇到 401 时，只发一次刷新请求，其余等同一个 Promise；刷新成功后各自重试原请求。否则 5 次刷新里只有第一次成功（轮换后旧令牌失效），其余 4 次会把用户踢下线。
- **在哪**：`fe/api/http.ts:32`（`refreshing` 变量）、`:34`（`refreshAccessToken`）。
- **怎么验证**：浏览器里把 localStorage 中的 accessToken 改成一个过期令牌，刷新首页，Network 面板里只有一次 `/api/auth/refresh`。

### 6. 防重复提交（一次性令牌）
- **是什么**：进编辑器时先申请一个提交令牌（Redis，10 分钟），发布时放在 `Idempotency-Token` 请求头里。服务端第一步 `DEL` 这个令牌，删成功才继续。双击、网络重试都只会成功一次。
- **在哪**：`service/article/SubmitTokenService.java:32`（`consume`）、`service/article/ArticleService.java:108`（`publish`）。
- **怎么验证**：跑 `IT/ArticleFlowIT.java:36`（`sameSubmitTokenOnlyWorksOnce`）。

### 7. 文章状态机
- **是什么**：DRAFT →（发布）→ PUBLISHED 或 PENDING（命中审核词）；PUBLISHED →（下架）→ OFFLINE →（恢复）→ PUBLISHED；PENDING →（通过/驳回）。每个转换都检查当前状态，状态不对返回 30004。
- **在哪**：`service/article/ArticleService.java:108`（`publish`）、`:179`（`approve`）、`:204`（`offline`）。
- **怎么验证**：跑 `IT/ArticleFlowIT.java:18`（`draftIsPrivateUntilPublished`）。

### 8. 唯一索引兜底并发
- **是什么**：注册时"先查用户名是否存在再插入"有并发窗口，两个请求可能都查到"不存在"。直接插入，靠 `uk_username` 唯一索引抛 `DuplicateKeyException` 再翻译成 20001。
- **在哪**：`service/user/AuthService.java:46`（`register`）；索引在 `V1__init_schema.sql:16`（`uk_username`）。
- **怎么验证**：跑 `IT/AuthIT.java:22`（`registerLoginAndMe`，重复注册得到 409）。

### 9. 文件上传：按魔数判断类型
- **是什么**：扩展名和 Content-Type 都是客户端说了算，可以伪造。读文件前几个字节判断真实格式（PNG 是 `89 50 4E 47`），对象名用随机 UUID，按月份分目录。
- **在哪**：`service/file/FileService.java:33`（`uploadImage`）、`service/file/ImageType.java`。
- **怎么验证**：跑单元测试 `ImageTypeTest`；或把一个 txt 改名成 .png 上传头像，会得到 10007。

### 10. 防 XSS
- **是什么**：Markdown 渲染成 HTML 后必须清洗再 `v-html`。
- **在哪**：`fe/components/MarkdownView.vue:11`（`sanitize`，DOMPurify）。
- **怎么验证**：发一篇正文含 `<img src=x onerror=alert(1)>` 的文章，打开详情页不会弹窗。

## 面试可能怎么问

1. **JWT 有什么优缺点？怎么让它能被撤销？**
   原理：无状态、验签即可，横向扩展方便；缺点是签发后无法撤销。本项目：短有效期 + 每个请求查一次用户状态缓存（Redis，命中率极高），封禁就改这个缓存。局限：等于每个请求多一次 Redis 访问，已经不是"纯无状态"；如果连状态都不查，封禁要等令牌过期才生效。

2. **为什么要双令牌？只用一个长期 JWT 不行吗？**
   原理：访问令牌频繁出现在请求里，泄露面大，所以要短；刷新令牌只在刷新时使用，可以存服务端、可撤销。本项目：刷新令牌存 Redis 并轮换。局限：需要维护刷新逻辑，前端要处理并发刷新。

3. **刷新令牌被盗了怎么办？**
   原理：轮换让每个刷新令牌只能用一次。本项目：攻击者和真实用户谁先用谁成功，另一方会收到 20006 被迫重新登录。局限：更严格的做法是检测到"旧令牌被重用"时作废整个令牌家族，本项目没有做。

4. **登录失败锁定会不会被人恶意利用来锁别人的账号？**
   原理：会，按用户名计数就有这个风险。本项目：锁 15 分钟自动解锁，并且登录接口按 IP 限流（每分钟 10 次）。局限：分布式攻击绕得过 IP 限流；更好的做法是失败多次后要求验证码，而不是直接锁定。

5. **防重复提交有哪些做法？**
   原理：前端按钮置灰（不可靠）、一次性令牌、业务唯一键、分布式锁。本项目：一次性令牌，`DEL` 成功才往下走。局限：令牌消费后如果业务失败，用户需要重新申请令牌（前端自动做了）。

6. **用户名唯一怎么保证？先查后插有什么问题？**
   原理：检查和插入不是原子的，并发会有两个都通过检查。本项目：只依赖唯一索引。局限：要处理好异常翻译；分库分表后唯一索引只在单库内有效。

7. **上传接口有哪些安全风险？**
   原理：伪造类型上传脚本、超大文件、路径穿越、覆盖他人文件。本项目：魔数检测类型、限制大小、随机对象名、只允许图片。局限：没有做图片内容审核和病毒扫描；没有限制单用户上传频率。

8. **拦截器里用 ThreadLocal 存当前用户，有什么要注意的？**
   原理：Tomcat 线程池复用线程，不清理会串到下一个请求。本项目：`afterCompletion` 清理；SSE 这类异步请求不会走 `afterCompletion`，所以在 `afterConcurrentHandlingStarted` 里也清理。局限：业务里开的异步线程拿不到当前用户，需要显式传参。
