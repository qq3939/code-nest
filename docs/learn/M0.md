# M0 骨架

## 这个里程碑做了什么

搭出一个"什么业务都还没有、但所有基础设施都已就位"的工程：后端拆成 api / core / service / web 四个 Maven 模块，依赖方向单一（web → service → core → api）；所有接口统一返回 `{code, message, data, traceId}`，异常由一个全局处理器翻译成错误码和 HTTP 状态码；每个请求带一个 traceId，贯穿日志和响应头；Long 型 ID 一律序列化成字符串，避免前端丢精度；Flyway 在启动时建好全部 19 张表；Docker Compose 编排 MySQL、Redis、RabbitMQ、MinIO（ES 在 `search` profile），每个服务都有健康检查，后端等依赖健康后才启动；前端是 Vue 3 + Vite 骨架，带 Axios 封装和路由；GitHub Actions 跑后端 `verify` 和前端构建。

## 知识点清单

### 1. Maven 多模块与依赖方向
- **是什么**：父 POM 统一管理版本（`dependencyManagement`），子模块只声明用什么。api 放 DTO/VO/枚举，core 放与业务无关的基础设施（Redis、MQ 拓扑、限流、JWT），service 放业务，web 放 Controller、拦截器、定时任务和启动类。
- **在哪**：`backend/pom.xml:21`（`<modules>`）。
- **怎么验证**：在 `code-nest-core` 的任何类里 import 一个 `service` 包的类，`./mvnw compile` 会失败——core 根本没有依赖 service，这就是"依赖方向单一"的物理保证。

### 2. 统一返回 + 错误码同时携带 HTTP 状态码
- **是什么**：`Result<T>` 包装所有返回；`ErrorCode` 枚举里每个错误码同时带业务码和 HTTP 状态码。业务码让前端区分细节（例如 20005 令牌过期 vs 10002 未登录），HTTP 状态码让 Nginx、浏览器、监控不解析 body 也能分大类。
- **在哪**：`core/result/Result.java:9`（`Result`）、`api/common/ErrorCode.java:7`（`ErrorCode`）。
- **怎么验证**：`curl -i localhost:8081/api/users/me`，看到 HTTP 401 且 body 里 `code=10002`。

### 3. 全局异常处理
- **是什么**：`@RestControllerAdvice` 把 `BizException`、参数校验异常、JSON 解析失败、上传过大、404 等翻译成统一格式；兜底的 `Exception` 只返回"系统繁忙"，详细堆栈只进日志，不把内部信息泄露给调用方。
- **在哪**：`web/handler/GlobalExceptionHandler.java:31`（`handleBiz`，业务异常）、`:37`（`handleBind`，校验）、`:79`（`handleUnknown`，兜底）。
- **怎么验证**：`curl -XPOST localhost:8081/api/auth/login -H 'Content-Type: application/json' -d '{}'`，返回 400 和 `code=10001`，`message` 里写着哪个字段不合法。

### 4. traceId 与 MDC
- **是什么**：过滤器在请求最开始生成（或沿用请求头里的）traceId，放进 SLF4J 的 MDC，日志格式里用 `%X{traceId}` 打出来，同时写进响应头 `X-Trace-Id`。用户报错时给出 traceId，就能在日志里搜到这次请求的全部日志。
- **在哪**：`web/config/TraceIdFilter.java:26`（`doFilterInternal`）；日志格式在 `application.yml:109`（`pattern`）。
- **怎么验证**：`curl -i localhost:8081/api/health -H 'X-Trace-Id: hello123'`，响应头里是同一个值；后端日志行里出现 `[hello123]`。

### 5. Long 精度问题
- **是什么**：雪花 ID 有 19 位，超过 JS `Number.MAX_SAFE_INTEGER`（2^53−1，16 位），前端 `JSON.parse` 后末几位会变。解决办法是把 `Long` 序列化成字符串。注意只处理包装类型 `Long`：计数用基本类型 `long`，仍然输出数字。
- **在哪**：`core/config/JacksonConfig.java:18`（`longToStringCustomizer`）；踩坑记录见 pitfalls P-001。
- **怎么验证**：跑 `IT/AuthIT.java:22`（`registerLoginAndMe`），它断言 `/api/users/me` 返回的 `id` 是字符串；或在浏览器控制台执行 `JSON.parse('{"id":1834567890123456789}').id`，看末尾变成了什么。

### 6. Flyway 数据库版本管理
- **是什么**：表结构写在 `V1__init_schema.sql`，种子数据在 `V2__seed_data.sql`。启动时 Flyway 按版本号执行没执行过的脚本，并记录在 `flyway_schema_history` 表。已执行的脚本不能再改（校验和会变），要改表结构就新增 V3。
- **在哪**：`backend/code-nest-web/src/main/resources/db/migration/`。
- **怎么验证**：连上 MySQL 执行 `SELECT version, description, checksum FROM flyway_schema_history;`。

### 7. Compose 健康检查与启动顺序
- **是什么**：`depends_on` 默认只等容器"启动"，不等服务"可用"（MySQL 容器起来后还要初始化十几秒）。给每个中间件配 `healthcheck`，后端用 `condition: service_healthy` 等它们真正可用。
- **在哪**：`docker-compose.yml:24`（`healthcheck`，MySQL 健康检查）、`:126`（`depends_on`，backend 等中间件健康后再启动）。
- **怎么验证**：`docker compose up -d` 后马上执行 `docker compose ps`，能看到 backend 一直是 `created`，直到其他服务变成 `healthy` 才启动。

### 8. springdoc 接口文档
- **在哪**：依赖在 `code-nest-web/pom.xml`，配置在 `application.yml:86`（`springdoc`）。
- **怎么验证**：浏览器打开 http://localhost:8081/swagger-ui.html。

### 9. 前端 Axios 封装
- **是什么**：拦截器统一加 `Authorization` 头、统一拆 `Result`、把非 0 的 code 变成 `ApiError` 抛出。
- **在哪**：`fe/api/http.ts:7`（`ApiError`）、`:102`（`unwrap`）。
- **怎么验证**：浏览器开发者工具 Network 面板里看任意请求的请求头。

### 10. IoC、依赖注入与自动配置
- **是什么**：对象不是自己 `new` 出来的，而是由 Spring 容器创建、按类型注入（IoC / DI）。本项目统一用构造器注入：字段写成 `final`，Lombok 的 `@RequiredArgsConstructor` 生成构造器，Spring 用它注入，对象一创建就是完整的、不可变的。同一类型有多个 Bean 时要说清楚用哪个：两个线程池用 `@Qualifier` 按名字选；计数的四个实现里，`RoutingCountService` 用 `@Primary` 当默认。`@SpringBootApplication` 里包含组件扫描，默认只扫启动类所在的包，而启动类在 `…codenest.web` 下，`core`、`service` 模块里的 Bean 会扫不到，所以写了 `scanBasePackages`。自动配置：引入 `spring-boot-starter-data-redis` 等 starter 后，Boot 按"类路径上有没有这个类、容器里是不是还没有这个 Bean"等条件自动注册 `StringRedisTemplate`、`RabbitTemplate`、`ObjectMapper`，本项目没有自己定义它们，只在 `application.yml` 里配连接信息；要改 Jackson 的行为，就注册一个 `Jackson2ObjectMapperBuilderCustomizer` 在自动配置的基础上追加，而不是自己定义一个 `ObjectMapper` 把整套默认配置换掉。
- **在哪**：`web/CodeNestApplication.java:15`（`scanBasePackages`）、`core/config/JacksonConfig.java:18`（`longToStringCustomizer`）、`service/outbox/OutboxPublisher.java:37`（`@Qualifier`）、`service/count/RoutingCountService.java:18`（`@Primary`）、`service/count/NaiveCountService.java:19`（`@RequiredArgsConstructor`）。
- **怎么验证**：在 `application.yml` 顶层加一行 `debug: true` 启动后端，启动日志里会打印 `CONDITIONS EVALUATION REPORT`，其中`RedisAutoConfiguration` 出现在 Positive matches（条件满足、生效了）；`OutboxPublisher` 构造器里打断点，看注入的 `executor` 线程名前缀是 `outbox-`。

## 面试可能怎么问

1. **为什么要拆多模块？单模块不行吗？**
   原理：模块是编译期的边界，依赖方向错了直接编译失败，比"约定"可靠。本项目：core 不依赖 service，所以基础设施代码不会反过来调用业务。局限：模块多了构建慢、跳转麻烦；小项目拆两层（api + app）也够。

2. **统一返回体里为什么既有业务码又用 HTTP 状态码？有人说全部返回 200 更简单。**
   原理：HTTP 状态码是给基础设施看的（缓存、重试、监控告警），业务码是给前端逻辑看的。本项目：401 让前端触发刷新令牌，429 让前端提示限流，同时业务码区分"过期"和"未登录"。局限：两套码要维护一致；有的团队用全 200 是为了绕开某些网关对非 200 的特殊处理。

3. **前端拿到的 ID 末尾几位不对，可能是什么原因？**
   原理：JS 的 Number 是 IEEE 754 双精度，整数只有 53 位精度。本项目：Jackson 对 `Long` 用 `ToStringSerializer`。局限：所有接口 ID 都变成字符串，前端比较时注意类型；只改包装类型是一个约定，计数如果用了 `Long` 也会变成字符串。

4. **traceId 是怎么串起一次请求的？异步线程里还有吗？**
   原理：MDC 底层是 ThreadLocal。本项目：过滤器写入 MDC，响应头回传。局限：线程池里的异步任务拿不到父线程的 MDC，需要在提交任务时手动复制（可用 TaskDecorator）；跨服务要靠请求头传递，正式项目一般用 OpenTelemetry。

5. **Flyway 脚本执行过之后发现写错了，怎么办？**
   原理：Flyway 记录每个脚本的校验和，改了已执行的脚本会启动失败。本项目：只能新增 V3 去修正。局限：开发阶段可以 `flyway repair` 或清库重来，生产绝不能改已执行的脚本。

6. **`depends_on` 能保证依赖服务可用吗？**
   原理：默认只保证容器启动顺序。本项目：配合 `healthcheck` 和 `condition: service_healthy`。局限：只在启动时等一次，运行中依赖挂了不管，应用自身要有重连能力。

7. **全局异常处理器兜底的 Exception 应该返回什么？**
   原理：不要把异常信息原样返回，可能泄露 SQL、路径等。本项目：返回固定文案 + traceId，详细堆栈进日志。局限：前端看不到具体原因，排查依赖日志检索。

8. **Spring Boot 自动配置是怎么实现的？**
   原理：`@SpringBootApplication` 带有 `@EnableAutoConfiguration`，它读取各个 starter 的 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` 里列出的配置类；这些类上的 `@ConditionalOnClass`、`@ConditionalOnMissingBean`、`@ConditionalOnProperty` 决定是否生效，所以"引入依赖就能用"，自己定义了同类型的 Bean，默认的就让位。本项目：没有自己定义 `StringRedisTemplate`、`RabbitTemplate`、`ObjectMapper`，Jackson 用 customizer 追加配置。局限：自动配置做了什么不直观，排查时要打开 `debug: true` 看条件报告。

9. **构造器注入和字段注入（`@Autowired` 写在字段上）有什么区别？**
   原理：构造器注入可以把依赖声明成 `final`，对象创建完就是完整的；依赖太多时构造器参数会很长，提醒你这个类职责太多；单元测试时直接 `new` 并传入假对象，不需要 Spring。字段注入写起来短，但依赖藏在字段里，测试时要靠反射或启动容器。本项目：全部用 `@RequiredArgsConstructor` 生成构造器；同类型多个 Bean 时用 `@Qualifier` 或 `@Primary`。局限：构造器注入下的循环依赖会在启动时直接报错——这其实是好事，逼你拆开循环。
