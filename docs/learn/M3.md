# M3 关注、通知、Feed

## 这个里程碑做了什么

这是整个项目最"分布式"的一个里程碑。业务操作（发文、点赞、评论、关注）不再直接调用下游，而是在同一个数据库事务里往 `outbox_message` 表写一条事件，事务提交后异步发到 RabbitMQ；发送失败由中继任务按指数退避重发。MQ 端是一个 topic 交换机分发到 notify / feed / search / rank 等队列，消费者手动 ack，失败后转进带 TTL 的重试队列（1s、5s、30s），重试耗尽进死信队列并落库，管理端可以重放。通知消费靠 `msg_id` 唯一索引做幂等；未读数通过 Redis Pub/Sub 广播到所有实例，持有该用户 SSE 连接的实例负责推送。关注动态 Feed 实现了 push（写扩散）、pull（读扩散）、hybrid（普通作者推、大 V 拉，默认）三种模式，用"分数 + 同分偏移量"的游标翻页，支持关注后回填和收件箱冷启动。

## 知识点清单

### 1. 本地消息表（Transactional Outbox）
- **是什么**：要同时"改数据库"和"发消息"，两者无法放进一个事务。做法是把消息也当成数据，和业务数据在同一个本地事务里写入 outbox 表，提交后再发送。只要数据库提交成功，消息就一定存在，最终一定能发出去。
- **在哪**：`service/outbox/OutboxService.java:38`（`Propagation.MANDATORY`：没有外层事务直接报错）。
- **怎么验证**：`docker compose stop rabbitmq`，然后点赞一篇文章——接口仍然成功，`outbox_message` 里多一条 `status=NEW`；`docker compose start rabbitmq`，几秒后它变成 `SENT`，作者收到通知。或者跑 `IT/MessageReliabilityIT.java:75`（`outboxRelayDeliversUnsentRows`）。

### 2. 发布确认（Publisher Confirm）与中继
- **是什么**：`rabbitTemplate.send` 返回不代表 Broker 收到了。开启 `publisher-confirm-type: correlated` 后，Broker 持久化后回一个 ack，此时才把 outbox 标记为 SENT。不可路由的消息（`returned`）直接标记 FAILED 并打告警日志，因为重试也没用。中继任务每 5 秒捞一次到期的 NEW 记录，**先**推迟下次重试时间**再**发送，防止慢发送被下一轮重复捞起。
- **在哪**：`service/outbox/OutboxPublisher.java:76`（`send`）、`:49`（`relayDue`）、`:70`（`backoff`）。
- **怎么验证**：在 `OutboxPublisher.send` 的 `whenComplete` 回调里打断点，观察 `confirm.isAck()`。

### 3. 重试队列 + 死信
- **是什么**：Spring 默认的重试是在消费线程里 sleep 重试，会阻塞后面的消息。本项目用 RabbitMQ 原生机制：消费失败时把消息转发到 `xxx.retry.N` 队列（设置了 TTL、没有消费者），过期后经 retry 交换机回到原队列；超过 3 次发到 dlx 交换机进入 `xxx.dlq`，再由死信消费者落库。消息体本身无法解析的直接 reject，由队列自带的死信交换机送进 dlq。
- **在哪**：`core/mq/RabbitTopologyConfig.java:30`（`rabbitTopology`，拓扑）、`core/mq/ConsumerSupport.java:28`（`handle`，失败处理）、`service/outbox/DeadLetterService.java:46`（`onDeadLetter`，落库）、`:73`（`replay`，重放）。
- **怎么验证**：跑 `IT/MessageReliabilityIT.java:50`（`failingMessageGoesToDeadLetterAndCanBeReplayed`）；或打开 http://localhost:15672 （RabbitMQ 管理台）看 Queues 页面里的 `.retry.1`、`.dlq` 队列。

### 4. 消费幂等
- **是什么**：MQ 只保证"至少一次"，网络抖动、消费者重启都会导致重复投递。通知表 `msg_id` 有唯一索引，重复插入抛 `DuplicateKeyException` 就当成功处理。排行加分用 Lua 把"去重标记 + 加分"做成一步。Feed 和搜索的消费天然幂等（ZADD、按 ID upsert）。
- **在哪**：`service/notify/NotifyService.java:45`（`handle`）、`lua/rank_add.lua`、`V1__init_schema.sql:152`（`uk_msg_id`）。
- **怎么验证**：跑 `IT/MessageReliabilityIT.java:36`（`duplicateMessageCreatesOnlyOneNotification`，同一个 msgId 发两次，只产生一条通知）。

### 5. 未读数：重新计数而不是 INCR
- **是什么**：插入通知和 `INCR unread` 不在一个事务里。若 INCR 失败，消息重试时会因为幂等被跳过，未读数就永久少 1。改为每次都 `COUNT` 一遍再 `SET`，自带纠错。`(receiver_id, is_read, create_time)` 索引让 COUNT 很便宜。
- **在哪**：`service/notify/NotifyService.java:165`（`refreshUnread`）。
- **怎么验证**：手动在 Redis 里把某用户的 `notify:unread` 改成 99，再给他点个赞，值恢复正确。

### 6. SSE 跨实例推送
- **是什么**：SSE 连接只存在于某一个后端实例的内存里，而产生通知的消费者可能在另一个实例。做法是消费者把"用户 ID:未读数"发到 Redis Pub/Sub 频道，所有实例都订阅，只有持有连接的实例真正推送。每 25 秒发一次注释行心跳，防止 Nginx 和浏览器把空闲连接断开。前端用 `fetch-event-source`，因为原生 `EventSource` 不能带 `Authorization` 头。
- **在哪**：`service/notify/NotifyService.java:172`（`refreshUnreadAndPush`）、`web/sse/SseHub.java:40`（`init`，订阅）、`:71`（`heartbeat`，心跳）、`fe/stores/notify.ts:27`（`connect`）。
- **怎么验证**：M6 的双实例演示里，用两个浏览器分别登录，即使连接落在不同实例，点赞后对方的小红点也会立刻变化。

### 7. Feed：推、拉、推拉结合
- **是什么**：
  - **push（写扩散）**：作者发文时把文章 ID 写进每个粉丝的收件箱 ZSet。读很快（一次 ZREVRANGE），但大 V 有几百万粉丝时写放大严重。
  - **pull（读扩散）**：每个作者只写自己的发件箱，读的时候把所有关注者的发件箱归并。写很便宜，但关注 500 人就要读 500 个 ZSet。
  - **hybrid（默认）**：粉丝数少于阈值（默认 5000）的普通作者推；大 V 只写发件箱，读时把"收件箱 + 关注的几个大 V 的发件箱"归并。
- **在哪**：`service/feed/FeedService.java:85`（`read`，读）、`:98`（`sourceKeys`，各模式的来源 ZSet）、`:248`（`onPublished`，发文）、`:299`（`fanout`，分批扇出）。
- **怎么验证**：跑 `IT/FeedIT.java:28`（`allModesReturnSameSequenceWithoutDuplicates`，三种模式翻页结果完全一致、无重复）；压测场景 3、4 对比读写耗时。

### 8. 只推给"收件箱已存在"的粉丝
- **是什么**：扇出时如果粉丝的收件箱不存在（很久没来，已过期），就跳过不推。否则会造出一个只有最新几条、缺失历史的残缺收件箱。等他来读时再从数据库冷启动重建最近 500 条。收件箱里放一个分数为 0 的占位成员，区分"空收件箱"和"不存在"。
- **在哪**：`lua/feed_push.lua`、`service/feed/FeedService.java:189`（`ensureInbox`，冷启动）。
- **怎么验证**：删掉某个用户的 `feed:inbox:{id}`，再打开他的关注页，Redis 里重新出现这个 key。

### 9. Feed 游标：分数 + 偏移量
- **是什么**：分数是发布时间毫秒数，可能重复。游标记录"上一页最后一条的分数 maxScore"和"该分数已经返回了几条 offset"，下一页从 `score <= maxScore` 开始并跳过 offset 条。同分时按文章 ID 倒序，保证排序稳定。
- **在哪**：`service/feed/FeedCursor.java:26`（`decode`）、`service/feed/FeedMerger.java:29`（`merge`）。
- **怎么验证**：单元测试 `FeedMergerTest` 里有一组全部同分的数据。

### 10. 消息乱序时以数据库为准
- **是什么**：关注后立即取关，两条消息可能乱序到达。消费者不信任消息里的"关注/取关"，而是去查数据库当前状态再决定回填还是移除；发文消息到达时文章可能已被删除，同样以数据库为准。
- **在哪**：`service/feed/FeedService.java:273`（`onFollowChanged`）、`:251`（`onPublished`）。
- **怎么验证**：跑 `IT/FeedIT.java:56`（`unfollowAndDeleteAreFiltered`）。

## 面试可能怎么问

1. **如何保证"写数据库"和"发消息"的一致性？**
   原理：两者不在一个事务里，先写库后发消息可能丢消息，先发消息后写库可能发出"幽灵消息"。常见方案：本地消息表、事务消息（RocketMQ）、CDC（Canal/Debezium 读 binlog）。本项目：本地消息表 + 提交后立即发送 + 中继兜底 + 发布确认。局限：outbox 表需要定期清理；最终一致，有秒级延迟；消息可能重复，下游必须幂等。

2. **RabbitMQ 怎么保证消息不丢？**
   原理：生产端确认（confirm）、Broker 持久化（durable 队列 + persistent 消息）、消费端手动 ack。本项目：三者都有，生产端还有 outbox 兜底。局限：单节点 Broker 磁盘坏了仍会丢，生产环境要用仲裁队列（quorum queue）。

3. **消费失败怎么重试？为什么不用 Spring 自带的重试？**
   原理：Spring Retry 在消费线程里阻塞重试，会卡住后面的消息，且重启后重试状态丢失。本项目：TTL 重试队列 + 死信交换机，延迟 1s/5s/30s，消息在 Broker 里等待，不占消费线程。局限：TTL 队列是队首过期才出队，所以每个延迟级别单独一个队列；需要更灵活的延迟可以用延迟消息插件。

4. **怎么保证消息幂等？**
   原理：给每条消息一个全局唯一 ID，下游用唯一约束或去重表判断。本项目：通知表 `msg_id` 唯一索引；排行用 Lua 原子地 SETNX + ZINCRBY；Feed/搜索的操作本身幂等。局限：去重标记要设过期时间，过期后的重复消息挡不住（实际几乎不会出现）。

5. **Feed 流推模式和拉模式怎么选？**
   原理：推是写扩散，读快写慢；拉是读扩散，写快读慢。本项目：hybrid，以粉丝数 5000 为界，压测报告里有三种模式的读耗时和大 V 发文的扇出耗时对比。局限：阈值是静态的；大 V 粉丝数在阈值附近波动时，其文章可能既在部分收件箱里又在发件箱里，归并时去重解决。

6. **Feed 分页为什么不用页码？**
   原理：Feed 不断有新内容插入，页码翻页会重复；ZSet 用分数做游标最自然。本项目：`maxScore + offset` 游标处理同分。局限：不能跳页；文章被删除后，游标定位仍然正确，但该页可能少于 size 条。

7. **多个后端实例时，SSE 怎么推送到正确的连接？**
   原理：长连接是有状态的，需要一个广播或路由层。本项目：Redis Pub/Sub 广播，每个实例只推本机持有的连接。局限：Pub/Sub 不持久化，实例短暂断开会漏消息——所以前端重连时会主动拉一次未读数；连接数很多时可以按用户 ID 路由，而不是全量广播。

8. **死信消息如何处理？**
   原理：死信说明自动重试解决不了，需要人工判断。本项目：落库展示错误原因，管理员修好问题后点"重放"，经 retry 交换机只回到原来那一个队列，不会让其他订阅者重复收到。局限：没有自动告警，只有 ERROR 日志。

9. **关注后立即取关，Feed 会不会出错？**
   原理：消息可能乱序或重复。本项目：消费者不信任消息内容，查数据库当前关注状态再操作。局限：多一次数据库查询；对于不需要强一致的场景，也可以用消息里的版本号/时间戳比较。
