# M4 排行、搜索、缓存、限流、敏感词

## 这个里程碑做了什么

这个里程碑把几个"高并发常用件"装上：活跃作者榜（日榜是 Redis ZSet，周榜和月榜由日榜 `ZUNIONSTORE` 合成，每天归档到 MySQL）和热门文章榜（按热度公式定时重算，原子 RENAME 替换）；Elasticsearch 全文搜索（IK 分词、高亮），ES 不可用或没开启时自动降级为 MySQL `LIKE`；文章详情的三种缓存模式（none / redis / two-level，默认两级：Caffeine + Redis），处理了缓存穿透、击穿、雪崩三大问题，删除失败走 MQ 补偿，多实例之间通过 Redis Pub/Sub 广播本地缓存失效；基于 ZSet 滑动窗口的 `@RateLimit` 注解，支持按用户、按 IP 多维度一次原子判断；前缀树敏感词，分拦截、审核、替换三级，命中审核级的文章进入待审。

## 知识点清单

### 1. ZSet 排行榜与周榜合成
- **是什么**：每个用户的活跃分记在当天的日榜 ZSet 里（发文 +10、评论 +2、被赞 +2、被收藏 +3，可在 `app.rank` 下配置）。周榜不单独维护，查询时把最近 7 个（月榜 30 个）日榜 `ZUNIONSTORE` 成一个 key，缓存 5 分钟。这样每次加分只写一个 key。
- **在哪**：`service/rank/RankService.java:79`（`addActiveScore`，加分）、`:86`（`activeRank`，查询与合成）、`:162`（`archive`，每天归档到 rank_snapshot）。
- **怎么验证**：在 Redis 里 `ZREVRANGE code-nest:rank:active:day:<今天> 0 9 WITHSCORES`，再看 http://localhost:8080/rank 页面。

### 2. 热度公式与原子替换
- **是什么**：`(点赞×2 + 收藏×3 + 评论×4 + 阅读×0.1) / (发布小时数 + 2)^1.5`，类似 Hacker News 的时间衰减。每 10 分钟对近 7 天的文章重算，先写 `:tmp` 再 `RENAME` 覆盖，读的人不会看到"算了一半"的榜单。
- **在哪**：`service/rank/HotScore.java:18`（`compute`）、`service/rank/RankService.java:122`（`refreshHotArticles`）。
- **怎么验证**：单元测试 `HotScoreTest`；修改公式里的指数 1.5，观察新文章和老文章的排序变化。

### 3. 搜索与降级
- **是什么**：ES 索引通过 search 队列异步同步（按文章 ID upsert / delete，天然幂等）。搜索先走 ES，ES 关闭或报错时降级为 `LIKE '%kw%'`（会全表扫描，但保证功能可用）。高亮先对原文做 HTML 转义，再插入 `<em>`，前端只需要信任 `<em>`。LIKE 的 `%`、`_` 需要转义，否则用户搜 `%` 会匹配所有文章。
- **在哪**：`service/search/SearchService.java:49`（`search`，入口与降级）、`:64`（`searchEs`，ES 查询与高亮，`encoder=html`，见 pitfalls P-024）、`:98`（`searchMysql`，MySQL 降级）、`:111`（`highlight`，安全高亮）、`service/search/SearchIndexService.java:63`（`upsert`，单篇 upsert）、`:86`（`reindexAll`，全量重建）、`service/search/ArticleDoc.java:29`（`publishTime`，日期字段的写入格式，见 P-022）。
- **怎么验证**：默认没开 ES，直接搜索就是降级路径；`.env` 里设置 `SEARCH_ENABLED=true` 后 `docker compose --profile search up -d --build`，搜索走 ES；已有的文章用管理端接口 `POST /api/admin/search/reindex` 全量写入索引；运行中 `docker compose stop elasticsearch`，搜索仍然能返回结果，日志出现 `fallback to mysql`，`start` 之后不用重启后端就会切回 ES。对比两条路径：搜"击穿缓存"（词序颠倒）或只在正文里出现的词，ES 能搜到，`LIKE` 搜不到。单元测试 `HighlightTest`、`ArticleDocMappingTest`。

### 4. 缓存穿透：缓存空值
- **是什么**：请求一个不存在的文章 ID，缓存永远不命中，每次都打到数据库。做法是把"不存在"也缓存起来（一个特殊标记，TTL 较短）。
- **在哪**：`service/cache/CacheService.java:156`（`writeRedis` 里的 NULL_MARKER）。
- **怎么验证**：跑 `IT/CacheIT.java:62`（`missingValueIsCachedAsNull`）。

### 5. 缓存击穿：互斥重建 / 逻辑过期
- **是什么**：热点 key 过期的瞬间，大量请求同时查库。
  - 普通 key 用互斥锁：未命中时 `SET lock NX PX`，抢到的去查库回填，没抢到的每 50ms 重读一次缓存，等约 1 秒仍无结果就直接查库（宁可多查一次，也不让请求失败）。释放锁用 Lua 比较 token，防止误删别人的锁。
  - 热门列表用逻辑过期：Redis 里不设 TTL，过期时间写在值里；过期后由一个线程异步重建，其他请求继续返回旧值。
- **在哪**：`service/cache/CacheService.java:125`（`readRedisOrRebuild`，互斥）、`:170`（`getLogical`，逻辑过期）、`:267`（`lockKeyOf`，锁 key 必须和数据 key 不同，见 pitfalls P-011）。
- **怎么验证**：在 `readRedisOrRebuild` 的 `loader.get()` 处打断点，用 JMeter 或几个并发 curl 请求同一篇没有缓存的文章，断点只命中一次。

### 6. 缓存雪崩：TTL 加随机抖动
- **是什么**：大量 key 同时过期（例如同一时刻预热的），会同时打到数据库。写入时 TTL 加 0～5 分钟的随机值，把过期时间打散。
- **在哪**：`service/cache/CacheService.java:161`（`jitter`）。
- **怎么验证**：打开几篇文章后 `TTL code-nest:cache:article:<id>`，每篇的剩余时间不同。

### 7. 先改库，提交后删缓存，失败走 MQ 补偿
- **是什么**：更新时删缓存而不是写缓存（写缓存在并发下更容易留下旧值）；删除放到事务提交之后（提交前删，别的请求可能把旧值又读回来）；删除失败把 key 发到 `cache.retry.queue` 重试。
- **在哪**：`service/cache/CacheService.java:231`（`evict`）、`:244`（`evictNow`）、`:288`（`sendDeleteRetry`，发送补偿消息）。
- **怎么验证**：跑 `IT/CacheIT.java:52`（`updateIsVisibleImmediately`，更新后立即可见）。

### 8. 两级缓存与失效广播
- **是什么**：本地 Caffeine 缓存（1 万条、60 秒）挡住绝大部分请求，连 Redis 的网络往返都省了；代价是多实例之间本地缓存不一致。删缓存时通过 Redis Pub/Sub 广播 key，所有实例清掉自己的本地副本；广播丢了，最多 60 秒后自然过期。
- **在哪**：`service/cache/CacheService.java:97`（`subscribe`，订阅）、`:105`（`get`，读路径）。
- **怎么验证**：跑 `IT/CacheIT.java:77`（`evictIsBroadcastToOtherInstances`）；M6 双实例演示。压测场景 1 对比三种模式的吞吐。

### 9. 滑动窗口限流
- **是什么**：每个维度一个 ZSet，成员是请求的唯一 ID，分数是时间戳。判断时先删掉窗口外的成员，再看数量是否超限。Lua 脚本"先全部检查、再全部写入"，避免 USER 维度放行、IP 维度拒绝时 USER 维度白白记一次。Redis 故障时放行（限流是保护措施，不应让整个接口不可用）。
- **在哪**：`core/ratelimit/RateLimitAspect.java:43`（`around`）、`lua/sliding_window.lua`（在 core 模块）、`core/ratelimit/RateLimitKeyResolver.java:16`（`resolve`）、各 Controller 上的 `@RateLimit`。
- **怎么验证**：跑 `IT/ArticleFlowIT.java:113`（`likeIsRateLimited`）；或者 1 秒内连续点赞 / 取消 6 次，第 6 次返回 HTTP 429。压测场景 5。

### 10. 前缀树敏感词
- **是什么**：把所有敏感词建成一棵字典树，对文本每个位置往下匹配，取最长命中。匹配时跳过空格和常见符号（"傻 * 瓜"也能识别）、大小写归一。三级处理：BLOCK 直接拒绝发布，REVIEW 进入待审，REPLACE 替换成等长的 `*`。管理员修改词库后，通过 Redis Pub/Sub 通知所有实例重新加载。
- **在哪**：`core/trie/SensitiveTrie.java:50`（`findAll`，匹配）、`:121`（`isSkippable`，跳过字符）、`service/article/ArticleService.java:246`（`review`，三级处理）、`service/sensitive/SensitiveWordService.java:51`（`reload`，重载）。
- **怎么验证**：单元测试 `SensitiveTrieTest`；跑 `IT/ArticleFlowIT.java:47`（`sensitiveWordsBlockReviewAndReplace`）。

### 11. 不加锁的并发：volatile + 不可变对象、本机去重
- **是什么**：敏感词树每次发文都要读，只有管理员改词库时才重建。重建时不在旧树上增删，而是建一棵新树，再把 `volatile` 字段整个换成新的：`volatile` 保证换完之后其他线程立刻看到新树；树建好后不再修改，读的线程拿到哪棵就用哪棵，不需要加锁，也不会读到建了一半的树。逻辑过期的缓存重建用 `ConcurrentHashMap.newKeySet()` 做本机去重：`add` 返回 `false` 说明本机已经有线程在重建这个 key，直接返回；跨实例再用 Redis `SET NX` 去重，两层都过了才提交到重建线程池。
- **关键细节**：`volatile` 只保证可见性和禁止指令重排，不保证复合操作的原子性，`count++` 这种"读-改-写"在 `volatile` 字段上照样会丢；这里能用，是因为写操作只有"整体替换引用"这一步。
- **在哪**：`service/sensitive/SensitiveWordService.java:42`（`trie`）、`:51`（`reload`）、`:59`（`check`）；`service/cache/CacheService.java:71`（`rebuilding`）、`:203`（`rebuildAsync`）。
- **怎么验证**：在 `SensitiveWordService.check` 和 `reload` 各打一个断点，管理端新增一个敏感词：`reload` 里 `trie` 被换成新对象（调试器里对象编号变了），之后的 `check` 读到的就是新对象。缓存去重：在 `application.yml` 的 `app.cache` 下加一行 `hot-list-logical-ttl: 5s`（默认 1 分钟），本机跑后端，管理端把缓存模式切到 redis（two-level 下请求会先被本地缓存挡住，走不到重建）。在重建任务里 `writeLogical` 那一行打断点，挂起方式选"线程"（Suspend: Thread），再在 `rebuildAsync` 开头 `if (!rebuilding.add(key))` 里的 `return` 打一个断点。5 秒后刷新首页"热门"：第一个请求提交了重建任务，重建线程停在 `writeLogical`，页面照常返回旧列表；再刷新一次，第二个请求停在 `return`，因为本机已经有线程在重建。

## 面试可能怎么问

1. **缓存穿透、击穿、雪崩分别是什么？怎么解决？**
   原理：穿透是查不存在的数据（缓存空值、布隆过滤器）；击穿是热点 key 过期（互斥锁、逻辑过期、热点永不过期）；雪崩是大量 key 同时过期或 Redis 宕机（TTL 抖动、多级缓存、限流降级）。本项目：空值缓存、互斥锁 + 逻辑过期、TTL 抖动 + 两级缓存。局限：空值缓存挡不住大量随机 ID 的攻击（没有做布隆过滤器）；互斥锁让等待请求多等几十毫秒。

2. **更新数据时，先删缓存还是先更新数据库？**
   原理：先删缓存，在更新数据库之前可能有读请求把旧值读回缓存；先更新数据库再删缓存，不一致窗口很小（需要"读请求在更新前读到旧值、在删除后才写入缓存"这种极少见的时序）。本项目：先更新库、提交后删缓存、失败 MQ 补偿。局限：仍然不是强一致；可以加延迟双删，或者订阅 binlog 删缓存。

3. **两级缓存怎么保证一致？**
   原理：本地缓存只在本进程有效，必须有失效通知。本项目：Redis Pub/Sub 广播 + 本地 60 秒短 TTL 兜底。局限：Pub/Sub 不保证送达，最坏情况 60 秒内读到旧值；本地缓存占用 JVM 堆，要控制条数。

4. **分布式锁用 `SETNX` 有哪些坑？**
   原理：要设置过期时间防止死锁；释放时要校验是不是自己的锁（Lua 比较后删除）；锁 key 不能和业务 key 相同；业务执行超过锁过期时间会导致锁失效（需要看门狗续期）。本项目：缓存重建锁用 SET NX PX + token；定时任务锁用 Redisson（带看门狗）。局限：Redis 主从切换时锁可能丢失，极端场景需要 RedLock 或 ZooKeeper。

5. **限流算法有哪些？为什么选滑动窗口？**
   原理：固定窗口（边界突刺）、滑动窗口（精确但存储大）、漏桶（匀速）、令牌桶（允许突发）。本项目：ZSet 滑动窗口，限额小（每秒 5 次），存储开销可忽略，而且能精确控制"任意 1 秒内不超过 5 次"。局限：限额大时 ZSet 成员很多，应改用令牌桶或滑动窗口计数器的近似算法。

6. **Redis 挂了，限流怎么办？**
   原理：要在"可用性"和"保护"之间选。本项目：放行（fail-open），因为限流只是保护措施。局限：如果限流是为了防止计费类接口被刷，就应该拒绝（fail-closed）。

7. **敏感词匹配为什么用前缀树？还有什么更好的办法？**
   原理：逐个词 `contains` 是 O(词数 × 文本长度)，前缀树是 O(文本长度 × 最长词长)。更进一步是 AC 自动机，失败指针让每个字符只看一次。本项目：前缀树 + 跳过符号 + 最长匹配。局限：没处理拼音、谐音、繁简转换。

8. **搜索为什么要异步同步到 ES？ES 挂了怎么办？**
   原理：同步写 ES 会拖慢发文接口，ES 故障还会让发文失败。本项目：通过 MQ 异步同步，消费幂等；ES 不可用时降级 MySQL LIKE。局限：异步有秒级延迟；LIKE 是全表扫描，数据量大时很慢，只能作为短时降级手段。

9. **排行榜的周榜、月榜怎么做？**
   原理：每个周期单独维护一个 ZSet 会让每次加分写多个 key；用日榜合成只写一个 key。本项目：按需 ZUNIONSTORE + 短缓存，每天归档前一天的榜单到 MySQL。局限：月榜要合并 30 个 ZSet，用户很多时合成较慢——缓存就是为了摊薄这个开销。

10. **`volatile` 能保证什么、不能保证什么？什么时候可以只用 `volatile` 不加锁？**
   原理：`volatile` 写入后其他线程立即可见，并禁止它前后的指令重排（双重检查单例要用它）；但不保证复合操作的原子性。只有写操作本身是一步（整体替换一个引用、设置一个标志位），或者只有一个线程写时，才能只用 `volatile`。本项目：敏感词树和运行时策略都是整体替换，读的地方不加锁；计数这种"读-改-写"就交给原子 SQL 或 Redis Lua。局限：替换期间正在用旧树的请求仍按旧词库判断，有一瞬间的新旧并存。
