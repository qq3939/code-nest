# M2 互动与计数

## 这个里程碑做了什么

实现点赞、收藏、两级评论（顶层评论 + 楼中楼回复）和评论点赞，以及文章计数（阅读、点赞、收藏、评论）和用户计数（文章数、粉丝数、关注数）。互动关系用"一行记录 + status 开关"保存，取消点赞不删行而是把 status 置 0，并用条件更新保证幂等。计数是本项目的第一个"可切换策略"的实验：naive（先读后写，会丢更新）、atomic-sql（`UPDATE … SET x = x + 1`，准确但每次都写库）、redis-batch（默认：Redis Hash 原子自增 + 脏集合 + 定时批量写回）。三种策略可以在管理端实时切换，集成测试把它们放在 200 线程 × 每线程 5 次的并发下对比，naive 1000 次里大约丢 977 次。夜间还有一个对账任务，以关系表为准修正计数。

## 知识点清单

### 1. 关系记录的幂等开关
- **是什么**：点赞关系第一次插入一行；之后取消/再点都只是 `UPDATE … SET status = #{to} WHERE id = ? AND status = #{from}`。返回值为 1 才说明"这次真的改变了状态"，只有这时才加减计数、发通知。重复点赞、并发点赞都不会重复计数。
- **在哪**：`service/interaction/RelationSwitch.java:23`（`activate`）、`service/interaction/mapper/LikeRecordMapper.java:11`（`switchStatus`）；唯一索引 `V1__init_schema.sql:93`（`uk_user_target`）。
- **怎么验证**：对同一篇文章连续调两次点赞接口，计数只加 1；在 `RelationSwitch.activate` 下断点，第二次走的是 `switchStatus` 并返回 0。

### 2. 事务提交后再做副作用
- **是什么**：点赞事务里只写关系表和 outbox；Redis 计数、日统计放在 `afterCommit` 里执行。如果在事务里改 Redis，事务回滚后 Redis 的改动不会跟着回滚，计数就错了。
- **在哪**：`service/common/AfterCommit.java:15`（`run`）、`service/interaction/LikeService.java:57`（`likeArticle`）。
- **怎么验证**：在 `LikeService.likeArticle` 的 `AfterCommit.run` 里打断点，观察断点命中时 MySQL 里 like_record 已经可以被另一个连接查到（事务已提交）。

### 3. 丢失更新（naive 策略）
- **是什么**：两个线程都读到 read=10，各自加 1 写回 11，结果少了一次。这是典型的"读-改-写"竞态。
- **在哪**：`service/count/NaiveCountService.java:30`（`increase`）。
- **怎么验证**：跑 `IT/CountConcurrencyIT.java:37`（`naiveLosesUpdates`），控制台会打印 `[count] naive: expected 1000, got xx, lost xx`。

### 4. 原子 SQL（atomic-sql 策略）
- **是什么**：`UPDATE article_stat SET read_count = read_count + ? WHERE article_id = ?`，由 InnoDB 行锁保证原子。准确，但热点文章的每次阅读都要抢同一行锁、写一次 redo log。
- **在哪**：`service/count/AtomicSqlCountService.java:28`（`increase`）、`service/count/mapper/ArticleStatMapper.java:14`（`increase`）。
- **怎么验证**：跑 `IT/CountConcurrencyIT.java:46`（`atomicSqlIsExact`）；压测场景 2 会比较它和 redis-batch 的 `Com_update` 次数。

### 5. Redis 计数 + 批量写回（redis-batch 策略，默认）
- **是什么**：一段 Lua 脚本原子地完成 `HINCRBY count:article:{id}` 和 `SADD count:dirty:article {id}`。定时任务每 10 秒 `SPOP` 一批脏 ID，读出 Hash 的**绝对值**批量 upsert 到 article_stat。写绝对值而不是增量，重复写回也不会翻倍；写库失败就把 ID 放回脏集合。
- **关键细节**：Hash 不存在时 Lua 返回 -1，由 Java 先从库里加载初值再重试。如果直接 HINCRBY，空 Hash 会从 0 开始，写回时就把库里原来的 10 万阅读覆盖成 1。
- **在哪**：`lua/count_incr.lua`、`service/count/RedisBatchCountService.java:60`（`increase`）、`:110`（`flush`）、`web/job/ScheduledJobs.java:41`（`flushCounts`）。
- **怎么验证**：跑 `IT/CountConcurrencyIT.java:53`（`redisBatchIsExactAfterFlush`）；或打开一篇文章后在 Redis 里 `HGETALL code-nest:count:article:{id}` 和 `SMEMBERS code-nest:count:dirty:article`，10 秒后脏集合变空、MySQL 里的值追上。

### 6. 策略路由与切换收尾
- **是什么**：业务代码只注入 `RoutingCountService`，它按运行时开关把调用转给三个实现之一。从 redis-batch 切走时必须先把 Redis 里的计数全部写回并清掉 Hash，否则切回来时会读到过期的值。
- **在哪**：`service/count/RoutingCountService.java:37`（`increase`）、`:52`（`beforeSwitch`）、`service/count/RedisBatchCountService.java:179`（`flushAndClear`）。
- **怎么验证**：管理端"实验开关"页切到 atomic-sql，Redis 里 `count:article:*` 被清空，MySQL 计数和切换前一致。

### 7. 对账
- **是什么**：每天凌晨 3 点，以关系表为准重新统计点赞、收藏、评论数；阅读数没有明细表，取 Redis 和库里较大的值。只修正有差异的行。
- **在哪**：`service/count/RedisBatchCountService.java:145`（`reconcile`）、`web/job/ScheduledJobs.java:68`（`reconcileCounts`）。
- **怎么验证**：手动把某篇文章的 `article_stat.like_count` 改成 999，在测试或调试中调用 `ScheduledJobs.reconcileAll()`，值被改回真实数量。

### 8. 两级评论与游标分页
- **是什么**：顶层评论 `parent_id = 0`，回复挂在顶层评论下（`parent_id` = 顶层 ID），并记录 `reply_to_user_id`，前端显示"A 回复 B"。列表用 `(create_time, id)` 组成的游标翻页，而不是 `LIMIT offset`：新评论插进来不会导致翻页重复或遗漏，深翻页也不变慢。
- **在哪**：`service/interaction/CommentService.java:55`（`create`）、`:110`（`listTop`）、`service/interaction/CursorCodec.java:21`（`encode`）。
- **怎么验证**：单元测试 `CursorCodecTest`；在详情页评论区连续点"加载更多"，Network 里看 `cursor` 参数。

## 面试可能怎么问

1. **点赞数这种高频计数怎么设计？**
   原理：直接写库会有行锁竞争和大量写 IO；放 Redis 原子自增，再异步批量落库。本项目：Lua 脚本自增 + 记脏，10 秒批量写回绝对值，夜间对账。局限：Redis 宕机且未持久化时，最多丢最近 10 秒的增量（对账能修复点赞/收藏/评论，阅读数修不回来）。

2. **为什么写回写的是绝对值而不是增量？**
   原理：增量写回不是幂等的，写回失败重试或任务重复执行都会多加。本项目：读 Hash 当前值 upsert，执行多少次结果都一样，测试里专门验证了重复 flush。局限：Hash 必须以库里的值为初值，否则会覆盖——这就是 Lua 返回 -1 的原因。

3. **naive 方式为什么会丢更新？除了原子 SQL 还有什么办法？**
   原理：读-改-写不是原子操作。办法：原子 SQL、悲观锁 `SELECT … FOR UPDATE`、乐观锁版本号重试、单线程串行化（队列）。本项目：测试实测 1000 次丢约 977 次。局限：乐观锁在热点行上会大量重试，不适合计数。

4. **取消点赞是删除记录还是改状态？**
   原理：改状态可以保留历史、避免频繁插删导致的索引页分裂，也方便条件更新做幂等。本项目：status 开关 + 唯一索引。局限：表只增不减，需要定期归档。

5. **在事务里操作 Redis 有什么问题？**
   原理：Redis 不参与数据库事务，回滚不会撤销 Redis 的修改；而且事务未提交时其他请求读库读不到新数据，会产生不一致。本项目：用 `TransactionSynchronization.afterCommit` 推迟到提交之后。局限：提交后、改 Redis 前进程崩溃，计数会少一次，靠对账修正。

6. **评论分页为什么不用 `LIMIT offset, size`？**
   原理：offset 越大扫描越多；数据在翻页过程中插入会导致重复或遗漏。本项目：`(create_time, id)` 游标，`id` 用来打破时间相同的平局。局限：不能直接跳到第 N 页。

7. **对账任务怎么避免一次加载全部文章？**
   原理：按主键游标分批（`WHERE id > ? ORDER BY id LIMIT 500`）。本项目：`ScheduledJobs.reconcileAll` 每批 500 篇。局限：文章量很大时仍然要跑很久，可以只对账"最近有变化"的文章。

8. **多实例部署时，写回任务会不会重复执行？**
   原理：每个实例都有自己的 `@Scheduled`，需要分布式锁。本项目：`JobLock` 用 Redisson 的 `tryLock`，拿不到就跳过（见 M3 / M6）。局限：即使重复执行，因为写的是绝对值，结果也是对的——这是"幂等"带来的额外安全感。
